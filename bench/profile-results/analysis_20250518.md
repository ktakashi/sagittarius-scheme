## Optimization Opportunities

### High Priority
1. **LREF + PUSH fusion** - LREF and PUSH often appear in sequence
   - Consider: LREF_PUSH_N (push N local refs at once)
   - Consider: LREF0_PUSH, LREF1_PUSH specialized variants

2. **Call frame optimization**
   - FRAME + GREF_CALL is extremely common pattern
   - Consider: FRAME_GREF_CALL combined instruction

3. **Branch+arithmetic fusion**
   - BNLT + ADDI often appear together in loops
   - Consider: Branch predictions or combined ops

### Medium Priority
4. **RET optimization**
   - Very frequent - ensure it's as fast as possible
   - Consider: RET_CONST, RET_LREF variants

5. **TAIL_CALL optimization**
   - Already exists but usage is low relative to regular CALL
   - Investigate why more calls aren't tail calls

### Low Priority (Already Optimized)
- LREF_PUSH already combines LREF+PUSH
- GREF_CALL already combines GREF+CALL
- GREF_TAIL_CALL already exists

## Recommendations

1. **Investigate LREF vs LREF_PUSH usage**
   - Why are there still separate LREF+PUSH sequences?
   - Compiler may not be emitting LREF_PUSH in all cases
   - Found: Combining happens in vm.scm via combine-insn-arg0
   - LREF+PUSH is combined UNLESS there's an intervening instruction (like UNBOX)

2. **Add FRAME+CALL fusion at compile time**
   - Most FRAME is immediately followed by CALL
   - Could save one dispatch per call
   - Note: FRAME_GREF_CALL would need complex encoding (3 args total)

3. **Profile more benchmarks**
   - boyer, browse, cpstak for diverse patterns
   - Real-world code may have different profiles

## Existing Optimizations (Already in Place)

The compiler already has extensive instruction combining:
- LREF + PUSH → LREF_PUSH
- FREF + PUSH → FREF_PUSH
- GREF + PUSH → GREF_PUSH
- CONST + PUSH → CONST_PUSH
- GREF + CALL → GREF_CALL
- GREF + TAIL_CALL → GREF_TAIL_CALL
- LREF + CAR → LREF_CAR
- LREF + CDR → LREF_CDR
- And many more...

## Phase 3 Optimization Plan

### 2. Hot Instruction Optimization
